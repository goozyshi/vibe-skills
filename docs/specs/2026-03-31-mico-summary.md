#### 一、基本信息 (Frontmatter)

**名称 (name)**
- 使用小写字母、数字、连字符，长度 ≤64 字符
- 动词开头，描述动作而非对象
- 示例：`pdf-processor`（非 `pdf`）、`gh-create-issue`（非 `github-tool`）

```yaml
name: mico-work-summary
```

**描述 (description)**

这是决定 Skill 何时被触发的**唯一依据**。AI 始终加载此字段，触发后才读取正文。

回答以下问题来撰写描述：
1. **功能边界**：这个 Skill 支持哪些具体功能？（列举 2-3 个核心场景）
2. **触发词汇**：用户会用什么词汇来描述这些需求？（记录典型表达）
3. **边界说明**：哪些相似但不支持的功能需要明确排除？

```yaml
description: |
  将原始工作记录（自然语言描述）转换为结构化工作报告，输出至 ~/mico-work-summary/YYYY/MM/YYYY-MM-DD.md。
  支持周报(weekly)、月报(monthly)、年报(yearly)三种时间跨度，周报节点默认为每周五。
  年报模式下同时生成两份报告：年度重点工作总结（面向协同方）+ 员工自评（含敏感数据与价值观复盘，面向评审方）。
  当用户提及"周报"、"月报"、"总结"、"年终自评"或要求整理工作记录时触发。
  不支持：项目计划制定、OKR 目标设定、非工作相关的个人日记。
```

> **反模式警告**：不要在 description 中使用尖括号 `<>`，字符数 ≤1024。

#### 三、核心工作流 (SKILL.md Body)

**工作流类型选择**

选择最契合任务特性的组织方式：
- [x] **决策树**（条件分支）：根据时间跨度参数(weekly/monthly/yearly)和节点状态(新建/迭代)选择不同路径

**输入约定**

- **工作记录**：自然语言描述，口语化输入即可，如"周一修了几个bug，周二开会讨论需求"
- **时间信息**：可选，支持"本周"、"上周五"、"3月24日"等表达方式，周报默认每周五为节点
- **月报/年报额外输入**：跨周期汇总时，用户需提供额外的趋势性描述、里程碑信息或特别强调事项
- **业务域信息**：用户输入中提及的业务名称（如"MicoWorld"、"SoulStar"），skill自动检查知识库，首次使用需用户简要说明业务背景，后续直接读取

**工作流草稿**

使用祈使句描述步骤，每个步骤 ≤2 行：

```markdown
## 解析输入与时间定位
解析用户输入的时间信息（本周/本月/本年/具体日期），周报默认节点为每周五
接收自然语言描述的工作记录作为输入
生成目标文件路径（基准目录 ~/mico-work-summary/）：
  - 周报：YYYY/MM/YYYY-MM-DD.md
  - 月报：YYYY/MM/YYYY-MM.md
  - 年报（双文件）：YYYY/YYYY-12-31-summary.md + YYYY/YYYY-12-31-self.md

## 判断节点状态
检查目标文件路径是否已存在
若不存在：执行【新建报告流程】
若已存在：执行【迭代更新流程】

## 新建报告流程（周/月/年报）
读取 references/report-structure.md 了解报告章节结构
加载 references/knowledge-base-ops.md 处理业务域：
- 提取业务名称，读取知识库获取业务类型、核心特性、历史主题
- 若业务不存在，按指南创建新业务条目
加载 references/classification-guide.md 提炼工作主题：
- 使用"分层理解策略"和"动作+对象提取法"推断主题方向
- 提供2-3个候选主题让用户确认
用户确认后生成业务进展总结（必填），风险与问题、解决方案、下一步计划按需生成
加载 references/knowledge-base-ops.md 更新知识库（追加主题到历史记录）
写入目标文件路径，追加迭代标记

## 迭代更新流程（详细设计）

### 步骤1: 读取与分析上下文
读取现有报告内容、元数据（迭代次数、最后更新时间）
加载 references/knowledge-base-ops.md 提取业务域并读取知识库（业务类型、核心特性、历史主题）
识别用户输入中的新增/变更事项，标注每项的：业务域、主题关键词、变更类型

### 步骤2: 主题一致性判断矩阵
判断新增事项与现有报告主题的关系：

| 关系类型 | 判断标准 | 处理方式 | 用户确认 |
|---------|---------|---------|---------|
| **同一主题延续** | 业务域相同 + 主题关键词匹配度>70% | 整合到现有段落，更新细节和进展 | 无需确认，直接合并 |
| **新增主题（同业务）** | 业务域相同 + 主题关键词全新 | 新增独立段落，保持与现有主题并列 | 提供主题选项让用户确认 |
| **跨业务补充** | 业务域不同 | 询问是否补充，确认后新增章节 | 必须确认 |
| **主题方向调整** | 相同工作被重新定性（如从"技术优化"改为"商业化支撑"） | 询问是否重新定义本周工作重点 | 必须确认 |
| **重复内容** | 事项描述与已有内容相似度>80% | 跳过，提示用户该内容已记录 | 提示但不阻塞 |

### 步骤3: 主题提炼（关键步骤）

**无论哪种变更类型，合并前必须先提炼主题**

加载 references/classification-guide.md 执行：
- 使用"分层理解策略"建立业务语境
- 使用"动作+对象提取法"从具体任务抽象到业务主题
- 参考历史主题列表，保持抽象层级一致
- 提供2-3个主题选项让用户确认

**错误做法**：直接将"完成P0需求「女用户成长评分策略调整」H5页面开发"写入报告  
**正确做法**：提炼为"用户分层运营能力建设"，具体实现作为支撑细节

### 步骤4: 内容合并策略

**4.1 补充细节（同一主题延续）**
- 先执行步骤3的主题提炼
- 定位现有报告中对应主题段落
- 检查是否重复：提取新增事项的核心动作+对象，与已有内容对比
- 如无重复：将提炼后的主题描述以补充句式追加（如" additionally"、"补充完成"）
- 如有重复：提示用户"该内容已在报告中记录：[引用原文]，是否需要更新？"

**4.2 新增主题（同业务域）**
- 先执行步骤3的主题提炼
- 参考历史主题列表，提供2-3个新主题选项
- 用户确认后，在业务进展章节新增段落（以提炼后的主题为核心）
- 控制总篇幅：若新增后超出50行，询问是否删减或合并次要内容

**4.3 跨业务域补充**
- 先执行步骤3的主题提炼（基于新业务背景）
- 检查新业务是否存在于知识库
- 若不存在：询问业务背景（类型/核心特性），创建知识库条目
- 若存在：读取业务特性，提供主题选项
- 在报告中新增该业务的独立章节（或合并到"其他业务进展"）

**4.4 修正信息**
- 如需修正主题定位：先重新提炼主题（步骤3），再定位替换
- 如仅修正细节：定位需要修正的段落，替换或更新描述，保持其他内容不变
- 可选：添加修正标记（如"_[更新于周六]_"）

### 步骤5: 知识库更新（条件触发）

加载 references/knowledge-base-ops.md 执行更新：
- 涉及新业务域 → 按指南创建新业务条目
- 涉及全新主题 → 追加到历史主题列表（按YYYY-MM）
- 发现新特性维度 → 更新核心特性列表

更新方式：追加模式写入，禁止覆盖已有内容

### 步骤6: 防重复与冲突检查

**重复检测机制：**
- 语义相似度检查：对比新增事项与已有内容的"动作+对象"组合
- 时间窗口检查：同一周期内（本周/本月），同一事项不应重复出现

**冲突检测机制：**
- 如果新增描述与已有描述矛盾（如"进展顺利"vs"遇到阻塞"）
- 询问用户以哪个为准，或是否需要调整表述

### 步骤7: 写入与标记更新
- 生成更新后的完整报告内容
- 迭代次数 +1
- 更新最后修改时间
- 可选：在变更章节添加迭代标记（如"_[第2次更新：补充XX内容]_"）

## 跨周期汇总（月报/年报特有）
扫描对应周期内所有子报告文件（如月报读取该月所有周报）作为参考素材
请求用户提供额外输入：跨周度的业务趋势、月度里程碑、需要特别强调的成果或风险
结合周报素材和用户补充输入，生成高层级总结，不重复罗列子报告细节

## 年终双报告流程（yearly特有）
当 period=yearly 时，同时触发两个生成流程：
- 年度重点工作总结：聚焦"做成了什么"，基于工作事实的重点产出整理（面向协同方）
- 员工自评：聚焦"做得怎么样"，基于岗位预期的自我评价与复盘（面向评审方）
两份报告分别输出至同一目录：yyyy/12/yyyy-12-31-summary.md 和 yyyy/12/yyyy-12-31-self.md

## 年度工作总结撰写要点
加载 references/yearly-summary-guide.md
- 聚焦最重要的几项工作产出，拒绝事无巨细的todo罗列
- 颗粒度适中：抓住关键举措 + 关键结果，提供具体业务数据
- 明确项目角色、进度、结果，拒绝假大空和拿来主义
- 不包含敏感数据/关键业务信息（此类内容放入自评的"核心业绩"）

## 年终自评撰写流程
加载 references/self-evaluation-guide.md 第一部分，理解双文档关系：
- 核心业绩：可补充敏感数据/关键业务信息（不方便在年度总结中公开的内容）
- 或输出全年工作思考：战略打法、关键举措、收获沉淀（与年度总结的事实陈述形成互补）
- 个人复盘：亮点与待提升点，基于岗位预期的自我评估

自评填写要点（加载 references/self-evaluation-guide.md 第二部分）：
- 对比预期：通过具体事例、行业数据对比，说明结果与预期差异
- 未来发展：针对需要提升或持续保持的部分，进行思考沉淀
- 成功经验：回顾做得好的部分，提炼可复制的方法论
- 根因分析：未达成部分深挖主观原因和客观原因，明确后续改善方向

撰写价值观部分时（可选），加载 references/self-evaluation-guide.md 价值观章节
- 引导用户基于四个价值观维度（正念/极端/简单/谦卑）选择最相关的1-2个
- 结合具体行为案例撰写，避免空泛表态

撰写管理自评部分时（可选，仅Leader），加载 references/self-evaluation-guide.md 管理维度章节
- 基于三个管理维度（管好业务/带好团队/传好文化）进行自我评估
- 结合团队管理实例说明管理实践和改进方向
```

> **简洁检查**：如果 SKILL.md 正文超过 500 行，考虑拆分内容到 references/。

**业务知识库 (business-knowledge.md)**

这是**运行时动态数据**，不是静态参考文档，单独说明：

| 属性 | 说明 |
|------|------|
| **存储路径** | `~/mico-work-summary/.knowledge/business-knowledge.md` |
| **数据格式** | 每业务域一个条目：`## 业务名称` 下含 `类型`、`核心特性`、`常见主题列表` |
| **读取时机** | 每次提取业务域后（判断是否存在该业务） |
| **写入时机** | 新建报告完成后（追加本次主题到历史记录） |
| **并发安全** | 单用户单会话写入，无需加锁；追加模式写入，禁止覆盖 |

```yaml
## MicoWorld
类型: 出海社交视频直播App
核心特性: [实时互动, 虚拟礼物, 主播PK]
历史主题:
  2025-03: [商业化变现-礼物动效, 社交互动功能-PK连麦]
```

#### 五、自由度分配

为每个步骤/功能标注约束强度，确保匹配任务特性。

| 步骤/功能 | 自由度   | 约束形式             | 理由                   |
| --------- | -------- | -------------------- | ---------------------- |
| 路径计算与文件定位 | 低 | calc-report-path.sh 脚本 | 日期计算逻辑复杂易错，必须精确 |
| 报告结构组织 | 中 | references/report-structure.md 模板 | 有标准四章节框架，但需根据业务灵活填充 |
| 工作事项分类提炼 | 高 | 文本指令 | 业务上下文差异大，需AI判断归类 |
| 风险与解决方案撰写 | 高 | 文本指令 | 需基于经验提炼，无法模板化 |
| 跨周期汇总摘要 | 中 | 伪代码逻辑 | 有提炼模式但需根据内容调整 |
| 迭代更新-主题一致性判断 | 中 | 伪代码（主题关系矩阵） | 有判断标准但需根据语义相似度灵活决策 |
| 迭代更新-内容合并策略 | 中 | 伪代码/文本指令 | 有合并模式（追加/替换/新增）但需根据内容判断具体类型 |
| 迭代更新-知识库更新 | 低 | 文本指令 + 严格数据格式 | 涉及持久化数据格式一致性，按固定格式读写，禁止覆盖 |
| 业务知识库管理 | 低 | 文本指令 + 严格数据格式 | 涉及持久化数据格式一致性，按固定格式读写，禁止覆盖 |
| 年终自评撰写（价值观/管理维度） | 高 | 文本指令 + self-evaluation-guide.md | 需结合个人实际案例，参考维度释义但不照搬 |

**三档位判断标准**：

- **高自由度（文本指令）**：多种做法皆有效，需上下文判断
  - 问：这个任务有 3 种以上正确做法吗？
  
- **中自由度（伪代码/参数化脚本）**：有推荐模式但允许调整
  - 问：存在"通常这样做"的模式，但需要根据情况微调吗？
  
- **低自由度（具体脚本）**：操作易错或必须严格一致
  - 问：错了会导致数据丢失/不可逆后果吗？

> **反模式警告**：避免全流程使用低自由度（过度刚性）或全流程高自由度（边界缺失）。
