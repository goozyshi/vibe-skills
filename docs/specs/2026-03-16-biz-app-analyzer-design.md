> **创建日期**：2026-03-16
> 	**状态**：待审核
> 	**Skill 名称**：biz-app-analyzer

---

## 一、概述

一个代码库分析 Skill，通过静态代码阅读自动生成结构化的 AI 知识库——四份 Markdown 文档，捕获项目上下文、架构机制、开发模式和领域词汇表。使后续 AI 会话无需用户反复解释即可深度理解项目。

支持两种使用模式：

- **全量分析**：首次使用，五阶段扫描代码库，生成完整的四文档知识库
- **增量更新**：代码库变更后，通过三层变更检测精准更新受影响的文档

通用化设计，不绑定特定框架或语言，通过五大机制模型适配前端、后端、全栈和移动端项目。

## 二、核心原则

### 2.1 分析机制，而非文件（Mechanisms over Files）

不生成文件系统的导览。一个请求可能流经三个文件——描述一次完整流程，文件只是路径上的节点。组织问题应该是"用户访问一个页面时会发生什么？"而非"router/index.ts 包含什么？"

### 2.2 记录连接，而非孤岛（Connections over Islands）

组件的价值不在于它接受什么 Props，而在于它如何与系统其他部分协作。CustomTable 的 `readParam` + `readURL` 模式配合 CustomSearchBar 的 `@update` 事件，构成一个完整的数据获取机制。文档应描述这个机制，而非两个孤立的组件说明。

### 2.3 捕获模式，而非实例（Patterns over Instances）

如果十个页面遵循相同的 CRUD 结构，描述一次模式并列出哪些页面遵循它。当 AI 构建第十一个页面时，它需要的是模式，不是十个示例的列举。

### 2.4 服务行动，而非理解（Action over Comprehension）

每条信息都应能帮助 AI 做出决策。检验标准："如果我正在实现一个 PRD 需求，这条信息是否帮我决定该做什么？"

"项目使用 Pinia 进行状态管理"是知识碎片。"用户权限存储在 permissStore——读取 `permissStore.userInfo.side_menus` 检查菜单权限，在路由守卫中调用 `permissStore.getUser()` 刷新鉴权状态"才是可执行的信息。

### 2.5 诚实反映，而非粉饰（Honest Reflection）

分析应如实反映代码库的实际状态。如果代码库混乱、没有一致的模式，文档应诚实地反映这一点，而非凭空编造不存在的模式。术语表应标记无法自信定义的术语，而非猜测含义。

## 三、产出物设计

### 3.1 四文档体系

Skill 生成四份 Markdown 文档，保存到项目根目录的 `.ai-docs/`：

| 文档 | 核心回答的问题 | 使用场景 |
|------|--------------|---------|
| `PROJECT_CONTEXT.md` | 这个项目是什么，代码如何组织，底层如何运作？ | 任何开发任务前必读，覆盖 80% 的项目理解需求 |
| `DEV_PATTERNS.md` | 给定一个新需求，在这个项目中的标准实现方式是什么？ | 实现新功能或 PRD 需求时参考 |
| `MODULE_MAP.md` | 对于某个具体页面/模块，涉及哪些路由、API、Store 和组件？ | 修改现有页面时查阅影响范围 |
| `GLOSSARY.md` | 项目特定术语是什么意思，PRD 术语如何映射到代码？ | 遇到陌生术语时查阅 |

**设计要点**：

- `PROJECT_CONTEXT.md` 是核心文档，一个 AI 只读这一份文件就应理解项目 80% 的工作所需
- 四份文档相互引用但各自独立可用，不存在必须全部读取才能理解的循环依赖
- 文档之间存在从"全局理解"到"局部查阅"的递进关系

### 3.2 质量标准

#### PROJECT_CONTEXT.md

- 项目概述应让从未见过代码库的人也能理解。描述产品做什么、谁在用、为什么存在——而非仅仅"一个 Vue 3 项目"
- 每个机制必须描述**流程**，而非仅列出文件。"请求经过 proxy.js 添加鉴权头、命中后端 /proxy/maidocha_svr/*、检查 20x 状态码、从 response.content 提取数据"是有用的。"proxy.js 处理 API 请求"没有价值
- 共享组件必须记录**协作模式**，而非仅列 Props。"CustomTable 监听 readParam 变化并从 readURL 自动拉取数据"告诉 AI 如何使用它。单独的 Props 表做不到
- 包含具体示例，用来澄清机制。一段典型页面调用 API 的代码片段，价值超过抽象描述

#### DEV_PATTERNS.md

- 每个模式必须有**触发条件**——什么样的 PRD 需求会映射到这个模式
- 每个模式必须列出**完整的文件清单**——需要创建和修改的所有文件，包括路由注册、i18n 条目等副作用
- 每个模式必须指定一个**参考页面**——真实存在的页面文件路径，AI 可以读取它作为具体模板
- 模式按使用频率排序，最常见的排第一

#### MODULE_MAP.md

- 每个页面都应列出路由路径、API 端点、Store、组件依赖
- 按业务模块分组，便于快速扫描
- 大型项目（50+ 页面）聚焦每个模块的关键页面，而非穷举所有页面

#### GLOSSARY.md

- 同时包含业务术语和技术术语
- 如果 PRD 语言与代码语言不同，必须显式映射
- 定义保持简洁——每个术语理想情况下一行

## 四、分析策略

### 4.1 五大机制模型

Phase 2 的核心分析围绕五大机制展开。这五大机制几乎存在于所有业务应用中，只是在不同项目类型中有不同的表现形态：

| 机制 | 核心问题 | 前端应用表现 | 后端服务表现 |
|------|---------|-------------|-------------|
| 请求层 | HTTP 请求如何发起、鉴权、错误处理？ | axios/fetch 封装 | API 框架中间件和 handler 模式 |
| 路由与导航 | URL 如何映射到页面，导航守卫如何工作？ | 客户端路由 | API 路由定义 |
| 状态管理 | 什么数据跨组件共享，如何共享？ | Pinia/Vuex/Redux 等 | 数据库模型和缓存层 |
| 鉴权与权限 | 用户如何认证，访问如何控制？ | 登录流程 + 路由守卫 + 页面内控制 | 中间件认证 + RBAC |
| 共享能力 | 存在哪些可复用的组件、Hook 和工具？ | UI 组件 + composables/hooks | 中间件 + 校验器 + 工具模块 |

**如果某个机制在项目中不存在（如 CLI 工具没有路由），则跳过。不强制套框架——记录实际存在的内容。**

### 4.2 取样-对比-泛化策略

Phase 3 的模式提取不是逐页阅读，而是遵循"取样-对比-泛化"的三步策略：

1. **广泛取样**：从不同业务模块挑选 2-3 个代表性页面（列表页、表单页、统计页等）
2. **完整阅读**：读取每个样本页的完整源码——模板、脚本、样式，记录所有导入、数据结构、交互流程
3. **跨样本对比**：寻找结构相似性——相同的组件编排？相同的数据获取模式？相同的表单提交流？
4. **抽象泛化**：将具体示例抽象为可复用模式，配以触发条件和参考页面

### 4.3 广度优先的模块扫描

Phase 4 与 Phase 3 相反——扫描大量页面但只提取浅层信息。对每个页面只读 `<script>` 部分的 import 语句和 API 调用，交叉引用路由配置，记录依赖指纹。

**规模适配策略**：

| 项目规模 | 页面数 | 扫描策略 |
|---------|--------|---------|
| 小型 | < 30 | 映射每个页面 |
| 中型 | 30-80 | 映射每个页面，简单页面允许简略条目 |
| 大型 | 80+ | 映射所有模块，每个模块聚焦 3-5 个关键页面 |

### 4.4 术语提取范围

Phase 5 从前四个阶段的全部发现中提取术语，同时额外扫描枚举文件、常量文件和 i18n 文件。

**纳入标准**（至少满足一条）：

- 业务领域术语：新人（人或 AI）不会立即理解的行业/产品术语
- 项目特定技术术语：含义偏离常规或代码库独有的技术词汇
- 缩写和首字母缩写：代码中无法自解释的缩写
- PRD-代码映射：产品团队与代码使用不同词汇时的对照关系

**排除标准**：通用编程概念、框架标准词汇、自解释的变量名。

## 五、工作流阶段详细设计

分析分为五个阶段执行，每个阶段建立在前一阶段的发现之上。

### Phase 1：项目扫描

**目标**：建立项目的技术档案——技术栈、文件组织方式和环境配置。

**具体操作**：

1. **定位项目根目录**：找到依赖清单文件（`package.json`、`requirements.txt`、`go.mod`、`Cargo.toml` 等）。单仓多应用时询问用户分析哪个应用
2. **识别技术栈**：从依赖清单提取核心框架及版本、UI 库、状态管理、构建工具、语言版本、其他影响代码编写方式的重要依赖
3. **扫描源码目录**：生成源码根目录 3 层深度的目录树，基于命名模式标注每个目录的角色（页面、组件、Hook、Store、API、路由、工具、类型、资源、国际化等）
4. **读取构建配置**：提取路径别名、开发服务器代理规则、环境差异配置、自动导入等构建时行为
5. **提取环境变量**：读取 `.env*` 文件，提取变量名（不含值），按用途分组（API 端点、特性开关、第三方服务）
6. **检查已有文档**：快速扫描 README.md、docs/、.cursor/rules/、CHANGELOG.md 等，记录存在情况

**产出**：`PROJECT_CONTEXT.md` 的项目概述、技术栈表、目录结构、环境配置部分的数据。同时形成后续阶段的文件定位线索（路由定义在哪？请求封装在哪？Store 在哪？共享组件在哪？页面组件如何组织？）。

**详细指引**：`references/phase-1-scanning.md`

### Phase 2：上下文分析

**目标**：理解项目的实际运作方式——数据如何流动、用户如何认证、页面如何渲染、共享代码如何使用。这是最重要的阶段，产出核心知识文档。

基于 Phase 1 定位的文件，逐一追踪五大机制的端到端流程：

#### 机制 A：请求层

找到 HTTP 客户端配置，提取每种请求模式的：基础 URL 策略、鉴权注入方式、请求生命周期（拦截器/成功处理/错误处理）、加载状态管理、多实例差异。

**输出要求**：描述为叙事性流程，而非文件说明。

#### 机制 B：路由与导航

找到路由配置的入口文件和模块定义文件，提取：路由模式（hash/history）、路由组织方式、布局结构、导航守卫链（从 URL 输入到页面可见的完整链路）、懒加载模式、路由元数据。

#### 机制 C：状态管理

读取每个 Store 文件，提取：职责范围、关键状态字段及类型、核心方法、缓存策略、消费模式。注意跨 Store 依赖关系。

#### 机制 D：鉴权与权限

追踪横跨多个文件的认证和权限逻辑，提取：认证流程、会话生命周期、路由级访问控制、页面内访问控制、权限数据来源。

**输出要求**：描述为完整流程链。

#### 机制 E：共享能力

分析共享组件、Hook/Composables、工具函数目录。

- 共享组件：记录用途、关键接口、**协作模式**、注意事项
- Hook/Composables：记录解决的问题、参数和返回值、典型用法
- 工具函数：仅记录高频使用或行为不直观的函数

**融合输出**：五大机制分析完成后，信息应自然交织。页面渲染涉及路由（B）触发鉴权检查（D）读取用户 Store（C）；页面使用共享组件（E）通过请求层（A）调用 API 填充 Store（C）。在写 `PROJECT_CONTEXT.md` 时让这些连接体现出来。

**产出**：填充 `PROJECT_CONTEXT.md` 模板的全部剩余部分。

**详细指引**：`references/phase-2-context-analysis.md`

### Phase 3：模式提取

**目标**：发现开发者在项目中构建功能时遵循的"配方"——从理解桥接到行动。

**具体操作**：

1. 从不同业务模块取样 2-3 个代表性页面
2. 完整阅读每个样本页面的源码（模板、脚本、样式）
3. 跨样本对比结构相似性
4. 将相似性抽象为可复用模式

**每个模式须包含**：

- **触发条件**：用 PRD 语言表述（"管理"、"列表"、"增删改查" → CRUD 管理页）
- **文件清单**：需创建和修改的完整文件列表，包含路由注册、i18n、权限配置等副作用
- **标准结构**：以叙事方式描述页面骨架和组件编排
- **数据流**：追踪页面主操作的数据生命周期
- **参考页面**：真实存在的示例页面文件路径

**副作用清单**：除页面组件本身外，还需记录"新页面启动税"——路由注册、菜单/侧边栏条目、国际化条目、权限配置、现有页面的链接更新。

**产出**：填充 `DEV_PATTERNS.md` 模板。

**详细指引**：`references/phase-3-pattern-extraction.md`

### Phase 4：模块映射

**目标**：构建查阅索引——AI 需要修改某个页面时，立即查看涉及的路由、API、Store 和组件。

**具体操作**：

对 views/pages 目录下的每个页面文件：

1. 仅读取 `<script>` / `<script setup>` 部分
2. 从 import 语句提取组件、Store、Hook、工具依赖
3. 扫描 API 调用（HTTP 函数调用、请求辅助函数）
4. 交叉引用路由配置获取路由路径
5. 记录页面目录下的本地子组件

按业务模块分组，每个模块附一行业务领域描述。

**交叉引用**：

- 页面遵循 `DEV_PATTERNS.md` 中的某个模式时标注引用
- 页面以非常规方式使用 `PROJECT_CONTEXT.md` 中记录的共享组件时引用说明
- 使用 `GLOSSARY.md` 中定义的领域术语

**产出**：填充 `MODULE_MAP.md` 模板。

**详细指引**：`references/phase-4-module-mapping.md`

### Phase 5：术语表生成

**目标**：提取项目特有的词汇表，防止 AI 误解领域术语。

**数据来源**：前四个阶段的全部发现 + 枚举文件 + 常量文件 + i18n 文件。

**结构分为两部分**：

- **业务术语**：术语、产品语境下的含义、PRD 中的别名（如有）
- **技术术语**：术语、在代码库中的含义/行为、出现位置

**质量检验**：取出任意术语，假设一个 AI 首次在代码中遇到它——定义是否提供了足够的上下文来正确使用？如果不够，定义需要更具体。

目标量：典型项目 15-40 个术语。

**产出**：填充 `GLOSSARY.md` 模板。

**详细指引**：`references/phase-5-glossary.md`

### Finalization：元数据文件与 Cursor Rule

五个阶段完成、四份文档写入 `.ai-docs/` 后，执行两项收尾操作：

**1. 写入 `.ai-docs-meta.json`**

项目当前状态的快照，供增量更新模式检测变更：

```json
{
  "generated_at": "ISO 8601 时间戳",
  "project_root": "绝对路径",
  "files_snapshot": {
    "views_modules": ["views/ 下的顶级目录列表"],
    "pages": ["views/ 下所有页面文件路径"],
    "components": ["components/ 下的文件/目录列表"],
    "hooks": ["hooks/ 或 composables/ 下的文件列表"],
    "stores": ["store/ 或 stores/ 下的文件列表"],
    "critical_files": {
      "path/to/request-wrapper": "最后修改 ISO 时间戳",
      "path/to/router-entry": "最后修改 ISO 时间戳",
      "path/to/auth-guard": "最后修改 ISO 时间戳",
      "path/to/main-entry": "最后修改 ISO 时间戳",
      "package.json": "最后修改 ISO 时间戳"
    }
  }
}
```

**2. 生成 `.cursor/rules/ai-docs.mdc`**

一条 Cursor Rule，指导后续 AI 会话如何消费知识库：

- 任何开发任务前读取 `PROJECT_CONTEXT.md`
- 实现新功能时读取 `DEV_PATTERNS.md` 和 `GLOSSARY.md`
- 修改现有页面时读取 `MODULE_MAP.md`
- 启动时检查文档新鲜度（与 `.ai-docs-meta.json` 对比）

Rule 设置 `alwaysApply: true`，确保在项目的每次对话中自动生效。

**详细指引**：`references/cursor-rule-template.md`

## 六、增量更新机制

当用户说"更新项目文档"时，不重跑全量分析，而是执行轻量的增量更新。

### 6.1 变更检测流程

**Step 1：加载基线**

读取 `.ai-docs-meta.json`，获取上次生成时的项目状态快照。如文件不存在，建议执行全量分析。

**Step 2：扫描当前状态**

收集与快照相同维度的当前信息：模块目录列表、页面文件列表、组件/Hook/Store 文件列表、关键文件修改时间。仅使用目录列举和文件 stat 操作，不读取文件内容。

**Step 3：计算差异**

对比产生六类 diff：模块增删、页面增删、组件/Hook/Store 增删、关键文件修改时间变化、距上次生成的天数。

### 6.2 三层响应机制

差异按影响程度分为三层，高层优先判定：

| 层级 | 触发条件 | 响应策略 | 影响的文档 |
|------|---------|---------|-----------|
| Tier 3：建议全量重生成 | 新增业务模块 / 关键架构文件被修改 / 距上次生成 > 30 天 / package.json 有变更 | 告知用户变更内容，建议重跑全量分析 | 所有文档可能过时 |
| Tier 2：定向更新 | 新增共享组件/Hook/Store（且未触发 Tier 3） | 读取新文件内容，分析接口和协作模式，更新 `PROJECT_CONTEXT.md` 对应章节 | `PROJECT_CONTEXT.md` |
| Tier 1：自动修复 | 页面增删（且未触发 Tier 3/2，或作为 Tier 2 的附加步骤） | 读取新页面 script 部分提取依赖指纹，更新 `MODULE_MAP.md` | `MODULE_MAP.md` |

**跨层处理**：diff 包含多层变更时，先处理 Tier 2（更新 `PROJECT_CONTEXT.md` 提供上下文），再处理 Tier 1（更新 `MODULE_MAP.md`）。

**边界情况**：

- **文件重命名**：在 removed 和 added 中同时出现相似文件名，可能是重命名。按删除 + 新增处理，内容可能已随名称变更
- **大批量新增**：新增超过 10 个页面时，重跑 Phase 4 整体比逐个添加更高效
- **删除引用检查**：删除组件/Hook/Store 时检查 `DEV_PATTERNS.md` 是否引用了被删除的项；删除页面时检查是否是某个模式的参考页面——如是则建议替换

### 6.3 元数据更新

任何更新完成后，重写 `.ai-docs-meta.json` 为当前项目状态，作为下次增量更新的新基线。

## 七、项目类型适配

五大机制模型通用于各类业务应用，但在不同项目类型中有不同的表现形态：

**前端应用**（SPA、SSR）：五大机制通常完整存在。请求层可能是 axios/fetch 封装；路由是客户端路由；状态管理因框架而异；共享能力包括 UI 组件和 composables/hooks。

**后端服务**（API 服务器、微服务）：请求层变为 API 框架的中间件和 handler 模式；路由变为 API 路由定义；状态管理变为数据库模型和缓存层；共享能力变为中间件、校验器和工具模块。

**全栈应用**（Next.js、Nuxt 等）：分别分析前端和后端层面，然后记录它们的连接方式（API routes、server actions、数据获取模式）。

**移动应用**（React Native、Flutter）：类似前端应用，但有平台特定的导航模式和原生模块集成。

**适配原则**：如果某个机制在项目中不存在（如简单的 CLI 工具没有路由），跳过它。不强制套框架——记录实际存在的内容。

### 8.1 输出目录结构

```
{project_root}/

│   ├── DEV_PATTERNS.md         # 开发模式手册

│   ├── GLOSSARY.md             # 领域术语表

└── .cursor/
    └── rules/
        └── ai-docs.mdc        # 自动生成的 Cursor Rule
```

### 8.2 .ai-docs-meta.json 设计

**用途**：记录生成时刻的项目状态快照，作为增量更新的对比基线。

**快照维度选择依据**：

| 快照字段 | 对应的变更检测目标 | 触发的更新层级 |
|----------|-------------------|-------------|
| `views_modules` | 新增/删除业务模块 | Tier 3 |
| `pages` | 新增/删除页面 | Tier 1 |
| `components` | 新增/删除共享组件 | Tier 2 |
| `hooks` | 新增/删除 Hook/Composable | Tier 2 |
| `stores` | 新增/删除 Store | Tier 2 |
| `critical_files` | 架构核心文件被修改 | Tier 3 |

`critical_files` 包含请求封装、路由入口、鉴权守卫、应用入口、依赖清单等架构级文件——这些文件的变动意味着 `PROJECT_CONTEXT.md` 中的机制描述可能失效。

### 8.3 Cursor Rule 自动生成

`.cursor/rules/ai-docs.mdc` 的核心指令：

- **开发任务前**：读取 `PROJECT_CONTEXT.md` 理解项目全貌
- **实现新功能时**：读取 `DEV_PATTERNS.md` 匹配模式，读取 `GLOSSARY.md` 理解领域术语
- **修改现有页面时**：读取 `MODULE_MAP.md` 了解依赖和影响范围
- **新鲜度检查**：比对 `.ai-docs-meta.json` 与当前项目状态，检测是否有新模块/新组件/超过 30 天未更新，发现漂移时建议用户运行增量更新

Rule 设置 `alwaysApply: true`、`globs` 留空（全局生效，非文件模式匹配）。每次全量分析或增量更新后覆写此文件。

## 十、关键设计决策

| 决策项 | 结论 | 理由 |
|--------|------|------|
| 产出物数量 | 四份独立 Markdown 文档 | 单一文档过长失去查阅价值，过多文档增加管理成本。四份对应四个不同使用场景（全局理解 / 开发行动 / 局部查阅 / 术语消歧），覆盖 AI 工作的完整链路 |
| 核心文档定位 | `PROJECT_CONTEXT.md` 覆盖 80% 需求 | AI 会话上下文有限，不应要求读取全部四份文档才能工作。一份核心文档 + 三份按需参考是最优的上下文分配策略 |
| 分析方法 | 机制驱动，非文件驱动 | 文件是代码的容器，机制才是理解的核心。描述"请求如何流转"比列举"每个文件包含什么"对 AI 决策更有价值 |
| 五大机制选择 | 请求层 / 路由 / 状态管理 / 鉴权 / 共享能力 | 这五个维度几乎覆盖所有业务应用的核心架构关注点，且在不同技术栈中都有对应表现，保证了跨框架通用性 |
| 模式提取策略 | 取样-对比-泛化 | 逐页阅读不可扩展，且会产生大量重复信息。取样 2-3 个代表性页面，从中泛化模式，既高效又能捕获 70-80% 的使用场景 |
| 模块映射深度 | 浅层扫描（仅 script + import） | Phase 4 的目标是建立索引而非深度理解。只读 import 和 API 调用足以构建依赖指纹，大幅降低分析成本 |
| 模式的参考页面 | 必须指定真实存在的文件路径 | 模式描述再完整也可能遗漏细节。AI 可以直接读取参考页面获得具体实现细节，弥补描述的抽象性 |
| 增量更新三层 Tier | Tier 1 自动修复 / Tier 2 定向更新 / Tier 3 建议全量 | 大多数变更是页面增删（Tier 1），自动修复成本极低。架构级变更（Tier 3）难以通过补丁可靠修复，建议全量重生成。三层覆盖了从轻到重的完整变更谱 |
| 变更检测方法 | 目录列举 + 文件 stat，不读内容 | 增量更新的检测阶段应尽可能轻量。目录和修改时间的对比足以判断变更类型和范围，无需读取文件内容 |
| critical_files 机制 | 监控少量架构核心文件的修改时间 | 请求封装、路由守卫、鉴权逻辑等文件的修改通常意味着架构变动，此时 `PROJECT_CONTEXT.md` 的机制描述可能失效，需要全量刷新 |
| 输出位置 | 项目根目录 `.ai-docs/` | 以 `.` 开头不污染项目主目录结构，与 `.cursor/` 等 AI 工具目录保持一致的命名惯例。项目内存储（而非全局）确保知识库与代码版本同步 |
| Cursor Rule 自动生成 | 每次分析后生成/覆写 `.cursor/rules/ai-docs.mdc` | 知识库生成后如果不告诉后续 AI 如何使用，价值大打折扣。自动生成的 Rule 解决了"知识库存在但无人读取"的问题 |
| 新鲜度检查 | Cursor Rule 指示 AI 在工作前比对 meta.json | 知识库的价值随时间衰减。自动化的新鲜度检查在知识库过期时主动提醒，而非等到 AI 输出错误信息后才发现 |
| 框架适配策略 | 通用五大机制 + 表现形态映射 | 不为每个框架写独立分析逻辑。五大机制在所有业务应用中普遍存在，只是具体表现不同，一套分析框架即可覆盖 |
| 术语表范围 | 15-40 个术语 | 过少无法覆盖领域词汇，过多沦为字典失去焦点。15-40 个恰好覆盖"非显而易见"的术语空间 |
| 静态分析局限性 | 明确声明，不掩盖 | 动态模式、运行时行为、反射机制等无法通过静态阅读完全捕获。诚实声明局限性比假装无所不知更有价值 |
| 单仓多应用处理 | 每个应用独立分析 | 单仓中不同应用通常有独立的技术栈和架构，混合分析会产生混乱。独立分析保证每份知识库的聚焦性 |

## 十一、局限性

1. **纯静态代码阅读**：不执行代码、不运行测试、不观察运行时行为。插件系统、反射机制、动态路由等动态模式可能被不完整地捕获。

2. **输出质量依赖代码库质量**：结构良好的代码库产出高质量文档，混乱的代码库产出价值有限的文档——但分析会诚实反映这种混乱，而非虚构模式。

3. **业务领域理解受限于代码线索**：业务领域的理解从代码结构、命名和注释推断。如果代码使用隐晦命名且无注释，领域分析将很浅。术语表会标记无法自信定义的术语。

4. **不适用于单仓根目录分析**：对于包含多个独立应用的单仓，应在每个应用的源码目录上分别运行分析，而非在仓库根目录。

5. **大文件上下文限制**：极大的源码文件可能超出 AI 的上下文窗口。分析会尽力覆盖但可能无法完整处理超大文件。
