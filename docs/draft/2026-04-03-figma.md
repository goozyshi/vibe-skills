## 前置检查

检测`.ai-docs`目录是否存在，决定执行模式：
- 存在 → 业务增强模式（完整流程）
- 不存在 → 通用模式（降级为基础Figma转码）

读取项目配置文件（如存在）：
- `.ai-docs/tech-stack.json` → 技术栈信息
- `.ai-docs/components.json` → 公共组件清单
- `.ai-docs/utils.json` → 工具函数清单

## Step 1: 解析Figma URL

从用户提供的URL提取：
- `fileKey`（设计文件ID）
- `nodeId`（节点ID，格式如"42-15"）

URL格式示例：`https://figma.com/design/{fileKey}/xxx?node-id=42-15`

## Step 2: 获取设计数据

调用Figma MCP工具获取设计数据：
- `get_design_context(fileKey, nodeId)` → 布局/颜色/字体/组件结构
- `get_screenshot(fileKey, nodeId)` → 视觉参考图（作为验证标准）

如果响应过大被截断：
- `get_metadata(fileKey, nodeId)` → 获取节点树结构
- 识别子节点ID
- 逐个调用`get_design_context(fileKey, childNodeId)`

## Step 3: 复用检查（业务增强模式专属）

### 3.1 识别可复用元素

从设计稿中识别常见UI模式：
- 按钮/输入框/选择器 → 表单组件
- 头像/徽章/标签 → 数据展示组件
- 卡片/列表项 → 布局组件
- 图标/图片 → 静态资源

### 3.2 扫描项目引用

使用grep查找组件使用情况：
```bash
grep -rn "import.*ComponentName" src/
grep -rn "<ComponentName" src/
grep -rn "class.*className" src/
```

提取关键信息：
- 引用文件路径（判断使用频率）
- 代码上下文（理解使用模式）
- Props配置（学习参数传递）

### 3.3 读取源码定义

定位组件源文件，提取：
- Props/Emits/Slots定义
- TypeScript类型约束
- 默认值和必填项
- 文档注释（@warn/@example/@deprecated）

对于CSS类，读取：
- 完整样式规则
- 依赖条件（如`.ellipsis`需配合`max-width`）
- 副作用（定位/层级/布局影响）

### 3.4 交叉验证

验证源码定义与实际使用的一致性：
- ✅ 案例符合源码API → 标记为推荐用法
- ⚠️ 案例存在非标准用法 → 标注警告
- 💡 源码能力未被充分使用 → 提示优化空间

### 3.5 展示复用方案并等待确认

以结构化格式展示：

```markdown

  <Avatar :src="user.avatar" size="0.8rem" :border="true" />

- 📂 源码：src/styles/common.less
- 🔍 项目引用：5处（100%都配合了maxWidth）
- ⚠️ 依赖：必须配合max-width使用
- 🎯 推荐用法：
  <div class="name ellipsis" :style="{maxWidth:'2rem'}">{{text}}</div>
```

## Step 4: 下载并处理资源

### 4.1 下载Figma资源

从Figma MCP响应中提取：
- 图片资源（PNG/JPG）
- SVG图标
- 字体文件（如有）

使用`localhost`源地址直接下载，不创建占位符。

### 4.2 图片优化处理

对每个图片资源执行：
```typescript
// 压缩并转换为webp
await sharp(imagePath)
  .webp({ quality: 80, effort: 6 })
  .toFile(outputPath);

// 保留原图作为降级方案（可选）
```

### 4.3 资源命名规范

按业务语义重命名（非文件名推测，需结合设计稿位置）：
```
{业务前缀}-{用途}-{描述}.{ext}

示例：
- user-avatar-default.webp
- btn-icon-close.svg
- game-bg-level-completed.webp
```

### 4.4 资源存放策略

根据使用范围决定路径：
- 组件专属 → `{ComponentName}/assets/`
- 多组件共享 → `src/assets/img/{business}/`

## Step 5: 布局分析（需用户确认）

### 5.1 间距测量

测量设计稿中元素间距，用符号化语法表示：
- `【A B】` → 横向布局（flex-direction: row）
- `【A + B】` → 纵向布局（flex-direction: column）
- `【A 0.32rem B】` → 带间距标注
- `【A 【B + C】】` → 嵌套结构

### 5.2 分组决策

根据间距一致性决定DOM结构：

| 间距情况 | DOM策略 | 示例 |
|---------|---------|------|
| 全部一致 | 平铺子元素，统一gap | `<div style="display:flex;gap:0.32rem">` |
| 部分不一致 | 嵌套分组，各组独立gap | `<div gap:0.64rem><div gap:0.32rem>` |

### 5.3 展示布局方案

```markdown

【头像 0.32rem 名字 0.32rem 金币 0.64rem 排名】
   ↑ 一致 ────────↑     ↑ 不一致 → 需分组

**分组方案**：
【【头像 名字】0.64rem【金币 排名】】
  ↑ gap:0.32rem    ↑ gap:0.64rem

**DOM树**：
根容器 (row, gap: 0.64rem)
├── 用户组 (row, gap: 0.32rem) → .item__user
│   ├── Avatar
│   └── Name
└── 数据组 (row, gap: 0.64rem) → .item__stats
    ├── Coin
    └── Rank

是否按此方案生成？(yes/no/adjust)
```

## Step 6: 代码生成

### 6.1 选择代码模板

根据`.ai-docs/tech-stack.json`选择：
- Vue 3 → `templates/vue-template.vue`
- React → `templates/react-template.tsx`

### 6.2 生成组件结构

**文件结构**：
```
{ComponentName}/
├── index.vue (或 index.tsx)
├── Example.vue (使用示例)
├── components/ (子组件，如有重复模式)
└── assets/ (组件专属资源)
```

**代码生成优先级**：
1. ✅ 先生成静态页面代码（保证布局正确）
2. ✅ 再添加交互逻辑（基于静态代码增强）
3. ❌ 禁止逻辑代码影响布局

### 6.3 应用项目规范

**样式处理**：
- Vue → 使用`<style scoped>`
- React → 根据项目选择CSS Modules/Styled Components/Tailwind
- 应用BEM命名：`.block__element--modifier`

**组件导入**：
```vue
<!-- Vue示例 -->
<script setup lang="ts">
// 复用的公共组件
import { Avatar, Button } from '@/components';
// 本地资源（使用import，非路径字符串）
import coinIcon from './assets/game-icon-coin.webp';
</script>
```

**Props策略**：
- 动态数据 → 定义Props
- 静态文案 → 使用默认值
- 缺失切图 → 占位div + emoji + TODO注释

```vue
<!-- 占位符示例 -->
<div class="trophy__placeholder" :style="{ width: '0.6rem', height: '0.6rem' }">
  🏆
</div>
<!-- ⚠️ TODO: 切图缺失 - 奖杯图标 | 尺寸60x60 | 路径待补充 -->
```

### 6.4 子组件拆分

| 条件 | 决策 |
|-----|------|
| 相同UI模式出现≥2次 | ✅ 拆分子组件 + v-for/map |
| 仅出现1次 | ❌ 直接写在主组件 |

### 6.5 生成Example文件

```vue
<template>
  <div class="example">
    <!-- 基础用法 -->
    <ComponentName />
    
    <!-- Props变体 -->
    <ComponentName :data="mockData" size="sm" />
    
    <!-- 事件演示 -->
    <ComponentName @click="handleClick" />
  </div>
</template>

<script setup lang="ts">
import ComponentName from './index.vue';

const mockData = { /* 示例数据 */ };
const handleClick = () => console.log('clicked');
</script>
```

#### 五、自由度分配

| 步骤/功能 | 自由度 | 约束形式 | 理由 |
| --------- | ------ | -------- | ---- |
| Step 1: URL解析 | 低 | 正则表达式+示例 | fileKey/nodeId提取逻辑固定，错误会导致Figma API调用失败 |
| Step 2: 获取设计数据 | 低 | MCP工具调用示例 | API调用参数固定，响应截断处理有标准流程 |
| Step 3.1-3.2: 识别元素+扫描引用 | 中 | 文本指令+grep命令模板 | UI元素识别需AI理解，但grep命令相对固定 |
| Step 3.3-3.4: 读源码+交叉验证 | 高 | 文本指令+验证原则 | 需根据不同组件灵活调整读取策略，源码结构多样 |
| Step 3.5: 展示复用方案 | 中 | Markdown模板+案例 | 展示格式固定，但内容需动态生成 |
| Step 4: 资源处理 | 低 | 脚本(optimize-images.ts) | 图片压缩参数固定，操作可完全自动化 |
| Step 5: 布局分析 | 中 | 符号化语法规则+案例 | 间距测量有方法论，但分组决策需判断 |
| Step 6.1-6.2: 选模板+生成结构 | 中 | 模板文件+替换规则 | 模板固定，但插值内容需动态计算 |
| Step 6.3: 应用项目规范 | 高 | 文本指令+示例代码 | 不同项目规范差异大，需读取.ai-docs灵活适配 |
| Step 6.4-6.5: 拆分子组件+Example | 中 | 判断条件+模板 | 拆分规则清晰（≥2次重复），但实现需灵活性 |
| Step 7: 视觉验证 | 高 | Checklist+人工判断 | 需AI对比screenshot与代码，主观判断多 |
| Step 8: 用户确认 | 低 | Markdown模板 | 展示格式固定 |

**三档位分布统计**：
- 低自由度（脚本/固定模板）：4个步骤 (33%)
- 中自由度（参数化模板/规则）：5个步骤 (42%)
- 高自由度（文本指令/判断）：3个步骤 (25%)

**设计理由**：
1. **为什么Step 4用低自由度脚本？**
   - 图片压缩参数（quality:80, effort:6）经过测试，适用于95%场景
   - 错误操作（如覆盖原图）可能导致资源丢失
   - 脚本确保一致性，避免AI每次选择不同的压缩参数

2. **为什么Step 6.3用高自由度？**
   - 项目规范差异极大（Tailwind vs CSS Modules vs Scoped CSS）
   - 组件库导入路径各异（@/components vs @company/ui vs ../../../）
   - 需AI读取.ai-docs后灵活生成import语句

3. **为什么Step 7用高自由度？**
   - 视觉对比需AI理解设计稿意图（如"按钮圆角是设计重点还是可妥协"）
   - 响应式布局验证需结合Figma约束和项目断点配置
   - 无法用硬规则覆盖所有视觉细节

**反模式检查**：
- ✅ 避免全流程低自由度（保留了42%的中自由度和25%的高自由度）
- ✅ 避免全流程高自由度（33%的低自由度确保关键操作不出错）
- ✅ 易错操作（URL解析、图片处理）使用了低自由度约束
