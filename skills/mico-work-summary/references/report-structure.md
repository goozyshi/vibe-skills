## 报告章节结构

工作报告采用固定章节结构：业务进展、风险与问题、解决方案、下一步计划。其中解决方案章节按需出现，其余三个章节固定出现，但风险与问题、下一步计划允许内容为空（写"无"）。

| 章节 | 出现规则 | 内容规则 |
|------|---------|---------|
| 业务进展 | 始终出现 | 必须有具体内容 |
| 风险与问题 | 始终出现 | 有内容则写内容，没有则写"无" |
| 解决方案 | 风险有内容时才出现 | 对应风险给出方案 |
| 下一步计划 | 始终出现 | 有内容则写内容，没有则写"无" |

### 1. 业务进展（必填，有内容）

**目标**：展示本周期的核心产出和业务影响

**内容要点**：
- 聚焦最重要的1-2个业务主题深入展开，避免平铺多个主题
- 从业务主题出发，而非任务清单
- 说明做成了什么，产生了什么影响
- 提供具体数据或案例支撑
- 关联业务目标或战略方向

**聚焦原则**：
- 周报不是"工作清单"，选择本周最重要的1-2个业务主题展开
- 次要工作合并为一句话带过（如"其他：配合完成数据核对"）或直接省略
- 如果必须提及多个主题，也应有主次之分（主主题详细展开，次主题简略提及）

**写作模板**（单一主题聚焦）：
```
本周聚焦 [业务主题]，通过 [关键举措] 实现了 [关键结果]。

具体进展：
- [产出1]：[具体描述 + 数据/案例]
- [产出2]：[具体描述 + 数据/案例]

业务影响：[对用户/业务指标/团队协作的影响]
```

**写作模板**（多主题需主次）：
```
本周聚焦 [主业务主题]，同时推进 [次主题简述]。

[主业务主题]进展：
- [关键举措与结果]

[次业务主题]进展：
- [简述，控制篇幅]

其他：配合完成XX例行支持工作。
```

**反模式示例**：
❌ "本周完成了3个需求开发"
✅ "本周聚焦商业化变现，上线礼物动效系统，首日礼物收入提升18%"

❌ "重构了UserService代码"
✅ "解决用户数据查询性能瓶颈，页面加载时间从3s降至0.5s，用户留存率提升5%"

❌ "主题A进展、主题B进展、主题C进展"（平铺罗列）
✅ "本周聚焦礼物商业化，上线3D动效系统；同时配合完成PK功能需求评审。"

### 2. 风险与问题（固定出现，可写"无"）

**目标**：暴露当前遇到的阻碍和潜在风险。询问用户"本周有遇到什么风险或阻碍吗？"，有则写入具体内容，没有则写"无"。章节始终存在，绝不跳过。

**内容要点**：
- 明确描述问题是什么
- 说明问题的影响（简要即可）
- 区分已确认问题 vs 潜在风险

**写作模板**：
```
当前遇到以下问题：

1. [问题名称]
   - 问题描述：[简要说明问题]
   - 影响：[对业务/用户的影响]

2. [潜在风险]
   - [可能发生的问题及影响]
```

**精简原则**：
- 问题描述控制在2-3行以内
- 不需要过度展开"具体表现"、"影响范围"、"紧急程度"等细节
- 如果问题已解决，简要提及即可，无需详细描述

**反模式示例**：
❌ "遇到了一些技术问题"（过于模糊）
✅ "支付回调接口超时，影响约500名用户充值"（简洁明确）

❌ "具体表现：XXX；影响范围：XXX；紧急程度：XXX；触发条件：XXX"（过度展开）
✅ "Android低端机存在卡顿问题，影响约15%用户"（点到即止）

### 3. 解决方案（风险有内容时才出现）

**目标**：说明如何应对风险与问题。仅当"风险与问题"章节有具体内容（不是"无"）时才出现此章节。如果风险章节写的是"无"，则跳过此章节。

**内容要点**：
- 针对上一章节提到的问题给出方案
- 说明方案思路和预期效果
- 如果方案不确定，说明需要什么支持

**写作模板**：
```
针对上述问题，计划采取以下措施：

1. [针对问题1]
   - 方案：[解决思路]
   - 预期效果：[改善程度]

2. [针对问题2]
   - 当前进展：[已尝试的方案]
   - 待明确：[需要进一步确认的信息]
```

**精简原则**：
- 方案描述控制在1-2行
- 不需要详细的"执行计划"、"时间安排"、"资源需求"
- 如果问题已解决，说明"已解决"即可

**反模式示例**：
❌ "继续优化代码"（过于模糊）
✅ "采用Redis缓存热点数据，预计降低数据库查询80%"（简洁明确）

### 4. 下一步计划（按需，用户提及时才写）

**目标**：明确后续的行动方向。如果用户没有主动提及后续安排，简单询问一句，用户说没有就跳过。

**内容要点**：
- 说明下周期的工作重点
- 标注关键时间节点（如有）
- 如果有依赖或风险，提前说明

**写作模板**：
```
下周计划：

**重点方向**：[下周期的核心主题]

**具体安排**：
- [行动项1]：[预期产出]
- [行动项2]：[预期产出]

**关键依赖**（如有）：[需要其他团队/资源配合的事项]
```

**精简原则**：
- 安排控制在2-3项
- 不需要详细到"周一做什么、周二做什么"
- 时间节点可选，不强求

**反模式示例**：
❌ "继续推进现有工作"（过于笼统）
✅ "聚焦直播间PK功能，目标周四完成核心交互逻辑"（明确具体）

## 信息不足时的引导策略

当用户提供的信息不足以生成高质量报告时，采用**渐进式提问**而非连珠炮式发问。

### 优先级排序

**P0 - 必须明确的信息**：
- 业务目标：这项工作是为了解决什么问题？
- 关键结果：做成了什么？有哪些产出？

**P1 - 重要但可推断的信息**：
- 业务影响：对用户/指标的影响（可基于目标推断）
- 问题严重程度：阻碍工作的程度（可基于描述推断）

**P2 - 次要信息**：
- 精确数据：如果用户只说"大概"、"好像"，不要强求精确数字，可以使用"显著提升"、"明显改善"等相对表述
- 技术细节：实现方式（通常不需要体现在报告中）
- 详细时间：具体几点几分（周粒度报告不需要这么细）

### 数据展示灵活性

**用户提供了精确数据**：
- ✅ "留存率从35%提升到42%"
- ✅ "页面加载从3秒降至0.5秒"

**用户只有模糊感知**：
- ✅ "留存率明显提升"
- ✅ "页面加载速度显著改善"
- ✅ "礼物点击率有所提升"

**不要做的**：
- ❌ 追问用户"具体是多少？"（如果用户不清楚）
- ❌ 臆造精确数字"预计提升20%"（没有依据时）
- ❌ 强调"需要提供数据"（增加用户负担）

### 提问示例

**单轮提问（推荐）**：
```
为了更好地提炼本周工作，请补充以下信息：
1. 这项工作的核心目标是什么？（解决什么问题/达成什么目标）
2. 有哪些关键产出或成果？（如果有数据更好，没有的话描述主要产出即可）

其他信息我会基于已有描述合理推断，生成初稿后您可以进一步调整。
```

**避免的提问方式**：
❌ 连续发问多轮，每次只问一个问题
❌ 询问过细的技术实现细节
❌ 要求用户提供标准格式的输入
❌ 追问"具体数据是多少"（如果用户已经表示"大概"、"好像"）

## 工作主题抽象方法论

从具体任务到业务主题的提炼是报告质量的关键。

### 抽象层级判断

参考业务知识库中的历史主题，保持一致的抽象层级：

**过于具体**（任务层级）：
- "实现了礼物动效渲染"
- "修复了支付回调bug"
- "优化了数据库查询"

**合适的抽象**（业务主题层级）：
- "商业化变现 - 礼物体系优化"
- "交易稳定性保障"
- "用户体验性能提升"

**过于宽泛**（战略层级）：
- "推进业务发展"
- "提升产品质量"
- "加强技术建设"

### 主题推测与确认流程

1. **识别关键词**：从用户描述中提取业务实体（产品功能、业务模块）

2. **关联业务特性**：基于业务知识库的核心特性，推测工作所属领域

3. **提供选项**：给出2-3个候选主题，附带简短解释

4. **用户确认**：用户选择或补充说明实际目标

**示例**：
```
用户输入："这周做了直播间礼物的3D动效"

识别关键词：直播间、礼物、3D动效
关联特性：虚拟礼物（商业化）、实时互动（用户体验）

提供选项：
1. 商业化变现 - 提升礼物吸引力，增加用户付费意愿
2. 用户体验优化 - 增强互动反馈，提升观看体验
3. 技术能力建设 - 建设3D渲染能力，为后续功能打基础

请选择最符合本周工作重点的主题，或补充说明实际目标。
```

### 主题命名规范

使用 "业务方向 - 具体目标/成果" 的格式。业务方向和具体目标都不是固定列表，而是根据用户所在业务域和实际工作推断得出。详见 `references/classification-guide.md` 中的主题提炼方法论。

## 跨周期汇总要点

### 月报：基于周报的提炼

**不要做的事**：
- ❌ 简单拼接各周报内容
- ❌ 重复罗列单周细节
- ❌ 保留所有风险与问题（部分已解决）

**要做的事**：
- ✅ 提炼跨周的业务趋势
- ✅ 说明关键里程碑事件
- ✅ 突出月度层面的模式和转折点
- ✅ 仅保留仍未解决的风险

**写作方法**：
1. 快速浏览所有周报，识别重复出现的主题
2. 询问用户：本月最重要的3件事是什么？
3. 基于用户反馈和周报素材，生成月度总结
4. 长度控制：约为单周报的2-3倍（非4倍）

### 年报：基于月报的再提炼

**重点关注**：
- 全年最重要的3-5项工作产出
- 业务阶段的转折点和关键决策
- 可量化的年度成果
- 跨季度的能力建设和积累

**避免陷阱**：
- 不要试图覆盖全年所有工作
- 不要平均分配笔墨给每个月
- 不要堆砌数据，选择最有说服力的指标

## 迭代更新的合并策略

### 变更类型识别

**补充细节**：
- 用户说："补充一下，周三还参加了XX会议"
- 策略：在对应章节追加内容，不改变原有叙述

**修正信息**：
- 用户说："数据记错了，应该是15%不是18%"
- 策略：精确定位并替换错误信息

**调整方向**：
- 用户说："我觉得这周重点不是变现，更偏向用户体验"
- 策略：重新提炼主题，可能需要重构章节内容（需用户确认）

### 合并冲突处理

如果新输入与已有内容存在矛盾：
1. 优先询问用户意图，而非自行决断
2. 说明冲突点："您之前提到XX，现在说YY，是要修正还是补充？"
3. 确认后再执行合并

### 保持连贯性

迭代更新时注意：
- 维持业务逻辑的前后一致
- 避免同一内容在不同章节重复
- 更新下一步计划时，检查是否与本周进展呼应

## 写作风格指南

### 语言要求

- 使用业务语言而非技术黑话
- 面向协作方（产品/运营/管理者）而非工程师
- 简洁明了，避免冗长从句
- 数据优先，但不堆砌数字

### 示例对比

| 技术化表达 | 业务化改写 |
|----------|----------|
| "重构了UserService的数据访问层" | "优化用户数据查询性能，响应速度提升60%" |
| "实现了分布式缓存架构" | "解决高并发访问瓶颈，支持同时在线用户从1万提升到10万" |
| "修复了3个P0 bug" | "解决影响充值的关键问题，挽回约5%的潜在收入损失" |
| "完成了XX需求开发" | "上线PK连麦功能，单场直播互动率提升30%" |

### 数据使用原则

**有效的数据**：
- ✅ 业务指标变化：日活+10%、留存率+5%
- ✅ 性能提升：加载时间从3s降至0.5s
- ✅ 规模增长：支持并发从1万到10万
- ✅ 收入影响：挽回5%损失、提升18%转化

**无效的数据**：
- ❌ 代码行数：写了500行代码
- ❌ 工时统计：工作45小时
- ❌ 任务数量：完成3个需求
- ❌ 会议次数：参加了7个会议
