# Mico Work Summary - 工作记录结构化工具

这个 skill 帮助将口语化的工作记录转换成结构化的工作报告，支持周报、月报、年报三种时间跨度。

## 核心原则

**聚焦业务价值，拒绝流水账**
- 提炼工作主题而非罗列任务清单
- 关注解决的问题和产生的影响
- 展现思考深度而非堆砌工作量

**保持记忆，复用知识**
- 首次提及业务时询问背景，后续自动读取
- 记录历史主题方向，辅助后续提炼
- 迭代更新时保持业务逻辑连贯性

**精简表达，控制篇幅**
- 周报控制在40-50行，避免过度展开
- 数据展示适度，不强求精确数字
- 风险问题点到即止，不过度描述细节

## 周报生成流程

### 步骤 1: 解析输入与路径计算

1. 解析用户输入的时间信息（本周/上周/具体日期），默认节点为每周五

2. 使用脚本计算目标文件路径：
   ```bash
   bash scripts/calc-report-path.sh <date> weekly
   # 输出: ~/mico-work-summary/YYYY/MM/YYYY-MM-DD.md
   ```

### 步骤 2: 判断是新建还是更新

检查目标文件是否已存在：
- 若不存在 → 继续步骤3（新建周报）
- 若已存在 → 跳转到[迭代更新流程](#迭代更新流程)

### 步骤 3: 新建周报

#### 3.1 加载周报结构

读取 `references/report-structure.md` 了解报告章节结构：
- 业务进展（必填，有内容）
- 风险与问题（固定出现，可写"无"）
- 解决方案（风险有内容时才出现）
- 下一步计划（固定出现，可写"无"）

#### 3.2 处理业务域与提炼主题

**业务域处理**：加载 `references/knowledge-base-ops.md`，执行：
1. 从用户输入提取业务名称（如"MicoWorld"）
2. 读取知识库获取业务类型、核心特性、历史主题
3. 若业务不存在，按指南创建新业务条目

**主题提炼**：加载 `references/classification-guide.md`，执行：
1. 使用"分层理解策略"建立业务语境
2. 使用"动作+对象提取法"从具体工作推断业务意图
3. 参考历史主题列表，保持抽象层级一致
4. 提供2-3个候选主题让用户确认

**错误示范**：直接将"做了礼物动效"写入报告
**正确做法**：提炼为"商业化变现 - 礼物体系优化"，具体实现作为支撑细节

#### 3.4 生成报告内容

根据选定主题和用户提供的工作记录生成报告。报告固定包含四个章节，其中两个章节允许内容为空：

**业务进展**（必填，有内容）：描述做成了什么，产生了什么影响
**风险与问题**（必填，可写"无"）：询问用户"本周有遇到什么风险或阻碍吗？"，有则写入具体内容，没有则写"无"
**解决方案**（按需，有风险时才出现）：仅当风险与问题章节有具体内容时才写入，否则跳过此章节
**下一步计划**（必填，可写"无"）：询问用户"后续有什么计划？"，有则写入具体内容，没有则写"无"

章节结构示意：
```
## 业务进展
[必有具体内容]

## 风险与问题
[具体内容] 或 "无"

## 解决方案
[仅当风险与问题有具体内容时才出现此章节]

## 下一步计划
[具体内容] 或 "无"
```

绝不臆造风险或计划来填充内容——没有就是"无"。

写作时注意：
- 使用业务语言而非技术细节堆砌
- 数据展示适度：用户提供了具体数字就使用，只是"大概"、"好像"就用相对表述（如"显著提升"）
- 控制篇幅：周报目标30-50行（章节少时自然更短，不要为凑长度而注水）
- 避免"完成了XX需求"这类流水账表达

**重要：避免业务主题平铺**
如果用户一周内涉及多个业务主题，不要写成"主题A进展、主题B进展、主题C进展"的列表式结构。应该：
- 聚焦1-2个最重要的业务主题深入展开
- 次要工作合并为一句带过（如"其他：配合完成了XX数据核对"）
- 或直接省略次要工作

#### 3.5 更新知识库

加载 `references/knowledge-base-ops.md`，执行：
- 追加本次主题到该业务的历史主题列表（按YYYY-MM）
- 如发现新特性维度，更新核心特性列表

**重要**：追加模式写入，禁止覆盖。

#### 3.6 写入文件并标记元数据

在报告末尾添加元数据：
```markdown
---
_最后更新: YYYY-MM-DD HH:mm_
_迭代次数: 1_
```

周报生成完成！

## 迭代更新流程

适用于所有报告类型（周报/月报/年报）的增量更新。

### 步骤1: 读取与分析上下文
1. 读取现有报告内容、元数据（迭代次数、最后更新时间）
2. 加载 `references/knowledge-base-ops.md`，提取业务域并读取知识库（业务类型、核心特性、历史主题）
3. 识别用户输入中的新增/变更事项，标注每项的：业务域、主题关键词、变更类型

### 步骤2: 主题一致性判断矩阵
判断新增事项与现有报告主题的关系：

| 关系类型 | 判断标准 | 处理方式 | 用户确认 |
|---------|---------|---------|---------|
| **同一主题延续** | 业务域相同 + 主题关键词匹配 | 整合到现有段落，更新细节 | 无需确认 |
| **新增主题（同业务）** | 业务域相同 + 主题全新 | 新增独立段落，保持并列 | 提供选项确认 |
| **跨业务补充** | 业务域不同 | 询问后新增章节 | 必须确认 |
| **主题方向调整** | 相同工作被重新定性 | 询问是否重新定义重点 | 必须确认 |

### 步骤3: 主题提炼（关键步骤）

**无论哪种变更类型，合并前必须先提炼主题**

加载 `references/classification-guide.md`，执行：
- 使用"分层理解策略"建立业务语境
- 使用"动作+对象提取法"从具体任务描述抽象到业务主题
- 参考历史主题列表，保持抽象层级一致
- 提供2-3个主题选项让用户确认

**错误做法**：直接将"完成P0需求「女用户成长评分策略调整」H5页面开发"写入报告
**正确做法**：提炼为"用户分层运营能力建设"，具体实现作为支撑细节

### 步骤4: 内容合并策略

**补充细节（同一主题延续）**
- 先执行步骤3的主题提炼
- 定位现有报告对应主题段落
- 检查重复：提取新增事项的"动作+对象"与已有内容对比
- 如无重复：将提炼后的主题描述以补充句式追加
- 如有重复：提示用户该内容已记录

**新增主题（同业务域）**
- 先执行步骤3的主题提炼
- 用户确认后，在业务进展章节新增段落（以提炼后的主题为核心）
- 控制篇幅：若超出50行，询问是否删减或合并次要内容

**跨业务域补充**
- 先执行步骤3的主题提炼（基于新业务背景）
- 检查新业务是否存在于知识库，不存在则询问业务背景
- 在报告中新增该业务的独立章节（以提炼后的主题为核心）

**修正信息**
- 如需修正主题定位：先重新提炼主题（步骤3），再定位替换
- 如仅修正细节：定位段落，替换或更新描述，保持其他内容不变

### 步骤5: 知识库更新（条件触发）

加载 `references/knowledge-base-ops.md` 执行更新：
- 涉及新业务域 → 按指南创建新业务条目
- 涉及全新主题 → 追加到历史主题列表（按YYYY-MM）
- 发现新特性维度 → 更新核心特性列表

**重要**：追加模式写入，禁止覆盖。

### 步骤6: 写入与标记更新
- 迭代次数 +1
- 更新最后修改时间
- 可选：在变更处添加迭代标记（如"_[补充于周六]_"）

## 月报生成流程

月报是基于多个周报的跨周期总结。

### 步骤 1: 路径计算与节点判断

1. 使用脚本计算月报路径：
   ```bash
   bash scripts/calc-report-path.sh <date> monthly
   # 输出: ~/mico-work-summary/YYYY/MM/YYYY-MM.md
   ```

2. 检查是否已存在：
   - 若不存在 → 继续步骤2（新建月报）
   - 若已存在 → 跳转到[迭代更新流程](#迭代更新流程)

### 步骤 2: 扫描周报素材

使用脚本扫描本月所有周报：
```bash
bash scripts/scan-period-reports.sh <month_start> <month_end> ~/mico-work-summary
# 输出: 该月内所有周报文件路径列表
```

### 步骤 3: 请求用户补充月度视角

询问用户：
- 本月最重要的业务趋势是什么？
- 有哪些跨周的里程碑事件？
- 需要特别强调的成果或风险？

### 步骤 4: 生成月报内容

参考 `assets/monthly-template.md` 和周报素材，生成月报：

**关键原则**：
- **不要**重复罗列各周细节
- **要**提炼跨周期的模式和趋势
- **要**说明关键决策和转折点
- 长度约为单周报的2-3倍（非4倍）

遵循周报的[步骤3.2-3.6](#步骤-3-新建周报)（业务域处理、主题提炼、内容生成、知识库更新、写入文件）。

## 年报生成流程

年报需要同时生成两份报告。

### 步骤 1: 路径计算

使用脚本计算年报路径：
```bash
bash scripts/calc-report-path.sh <date> yearly
# 输出两个路径：
# ~/mico-work-summary/YYYY/YYYY-12-31-summary.md
# ~/mico-work-summary/YYYY/YYYY-12-31-self.md
```

### 步骤 2: 扫描全年报告素材

使用脚本扫描全年月报（如果有）或周报：
```bash
bash scripts/scan-period-reports.sh <year_start> <year_end> ~/mico-work-summary
```

### 步骤 3: 生成年度工作总结 (summary.md)

**定位**：面向协同方，展示"做成了什么"

1. 加载 `references/yearly-summary-guide.md` 了解写作要点：
   - 聚焦最重要的3-5项工作产出
   - 提供关键举措 + 关键结果
   - 包含具体业务数据
   - 明确项目角色、进度、结果
   - **不包含**敏感数据/关键业务信息

2. 使用 `assets/yearly-template.md` 作为结构骨架生成报告

### 步骤 4: 生成员工自评 (self.md)

**定位**：面向评审方，展示"做得怎么样"

1. 加载 `references/self-evaluation-guide.md` 了解自评结构

2. 使用 `assets/yearly-self-template.md` 作为结构骨架

3. 包含以下部分：

**第一部分：核心业绩与工作思考**
- 补充年度总结中不便公开的敏感数据
- 或展开全年工作的战略打法、关键举措、收获沉淀

**第二部分：个人复盘**（必填）
- 对比预期、未来发展、成功经验、根因分析

**第三部分：价值观**（可选）
- 基于正念/极端/简单/谦卑四个维度选择1-2个
- 结合具体行为案例撰写
- **详细参考**：加载 `references/values-framework.md`（四维度释义、行为准则、撰写指引）

**第四部分：管理自评**（仅 Leader，可选）
- 管好业务、带好团队、传好文化
- **详细参考**：加载 `references/leadership-framework.md`（三维度释义、自评关注点、结构参考）

详细指导请查阅 `references/self-evaluation-guide.md`。

## 常见问题

**Q: 用户输入信息不足怎么办？**
A: 引导式提问，但避免连珠炮式发问。优先询问最关键的信息（业务目标、关键结果），次要细节可基于已有信息合理推断并让用户确认。如果用户只说"大概"、"好像"，不要强求精确数字。

**Q: 追加内容时如何避免像截图那样平铺具体任务？**
A: **关键：追加前必须先执行主题提炼**

**错误示例**（直接追加原始描述）：
- 用户输入："完成 P0 需求「女用户成长评分策略调整」H5 页面开发"
- 错误结果：直接写入"完成 P0 需求...H5 页面开发"（平铺任务）

**正确示例**（先提炼再追加）：
- 步骤1：提炼主题 → "用户分层运营能力建设"
- 步骤2：确认关系 → 与现有"用户成长体系"主题属于同一业务域，可整合
- 步骤3：追加方式 → 在"用户成长体系"段落追加："补充完成用户评分策略 H5 页面，支撑分层运营能力"

**核心原则**：迭代更新的第3步（主题提炼）必须在第4步（内容合并）之前执行，不可跳过。

**Q: 迭代更新时如何避免内容冲突？**
A: 使用主题一致性判断矩阵识别新增事项与现有内容的关系：
- 语义相似度检查：对比"动作+对象"组合，避免重复记录
- 时间窗口检查：同一周期内同一事项不应重复
- 冲突处理：如果新增描述与已有描述矛盾，优先询问用户以哪个为准
- 重复提示：如发现用户补充的内容已记录，提示"该内容已在报告中记录：[引用原文]，是否需要更新？"

**Q: 跨周期汇总时如何控制长度？**
A: 月报基于周报提炼，不是简单拼接。关注跨周的趋势变化和里程碑事件，单周细节可以省略。年报同理。

**Q: 新增内容时如何与已有内容整合？**
A: 遵循"先提炼，后合并"原则：
1. **先提炼主题**：使用"动作+对象提取法"，从具体任务（如"完成P0需求XX开发"）抽象到业务主题（如"用户分层运营能力建设"），参考历史主题列表提供选项让用户确认
2. **再执行合并**：
   - **同一主题延续**：整合到现有段落，以补充句式追加（如" additionally"、"补充完成"）
   - **新增主题（同业务）**：新增独立段落，参考历史主题列表提供选项让用户确认
   - **跨业务补充**：询问用户后新增该业务的独立章节
   - **篇幅控制**：若整合后超出50行，询问是否删减次要内容或合并主题

**Q: 如何控制周报篇幅？**
A: 目标40-50行。业务进展10-15行，风险问题5-8行，解决方案5-8行，下一步计划5-8行。避免过度展开细节。

## 反模式警告

**流水账式汇报：平铺罗列任务清单**
- 问题：读者陷入细节，无法快速理解工作价值
- 做法：将具体任务归纳到业务主题下，说明"做成了什么"而非"做了什么"
- 示例：❌"本周完成了需求A、需求B、需求C" → ✅"本周聚焦商业化变现，通过优化礼物体系提升转化率"

**业务语言缺失：技术细节堆砌**
- 问题：业务读者难以理解技术术语，无法评估实际影响
- 做法：将技术动作翻译为业务结果，用数据说明改进效果
- 示例：❌"重构了UserService，优化了数据库查询，修复了3个bug" → ✅"解决了用户数据查询性能瓶颈，页面加载时间从3s降至0.5s"

**可信度损失：假大空表述**
- 问题：缺乏事实支撑，无法验证真实贡献
- 做法：明确角色定位（主导/参与/支持），提供量化结果
- 示例：❌"深度参与项目，全力推进业务发展" → ✅"主导XX功能设计与实现，上线后日活提升15%"

**数据安全风险：覆盖业务知识库**
- 问题：覆盖写入导致历史主题丢失，影响后续分析连贯性
- 做法：仅使用追加模式写入；如需修正，先读取全文再整体更新
