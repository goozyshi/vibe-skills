# Mico Work Summary - 工作记录结构化工具

这个 skill 帮助将口语化的工作记录转换成结构化的工作报告，支持周报、月报、年报三种时间跨度。

## 核心原则

**聚焦业务价值，拒绝流水账**
- 提炼工作主题而非罗列任务清单
- 关注解决的问题和产生的影响
- 展现思考深度而非堆砌工作量

**保持记忆，复用知识**
- 首次提及业务时询问背景，后续自动读取
- 记录历史主题方向，辅助后续提炼
- 迭代更新时保持业务逻辑连贯性

**精简表达，控制篇幅**
- 周报控制在40-50行，避免过度展开
- 数据展示适度，不强求精确数字
- 风险问题点到即止，不过度描述细节

## 周报生成流程

### 步骤 1: 解析输入与路径计算

1. 解析用户输入的时间信息（本周/上周/具体日期），默认节点为每周五

2. 使用脚本计算目标文件路径：
   ```bash
   bash scripts/calc-report-path.sh <date> weekly
   # 输出: ~/mico-work-summary/YYYY/MM/YYYY-MM-DD.md
   ```

### 步骤 2: 判断是新建还是更新

检查目标文件是否已存在：
- 若不存在 → 继续步骤3（新建周报）
- 若已存在 → 跳转到[迭代更新流程](#迭代更新流程)

### 步骤 3: 新建周报

#### 3.1 加载周报结构

读取 `references/report-structure.md` 了解标准四章节结构：
- 业务进展
- 风险与问题
- 解决方案
- 下一步计划

#### 3.2 处理业务域与知识库

从用户输入中提取业务名称（如"MicoWorld"、"SoulStar"）：

1. 检查业务知识库是否存在该业务：
   ```bash
   # 知识库路径: ~/mico-work-summary/.knowledge/business-knowledge.md
   ```

2. 若业务不存在，询问用户业务背景：
   - 业务类型（如：出海社交视频直播App）
   - 核心特性（如：实时互动、虚拟礼物、主播PK）
   
   按以下格式创建新条目：
   ```markdown
   ## <业务名称>
   类型: <业务类型>
   核心特性: [<特性1>, <特性2>, <特性3>]
   历史主题:
     <YYYY-MM>: []
   ```

3. 若业务已存在，读取业务特性及历史主题记录

#### 3.3 提炼工作主题

**关键方法：从具体事项到抽象主题**

基于业务特性和用户描述的具体工作，推测可能的主题方向，提供选项让用户确认。

参考 `references/classification-guide.md` 中的分类维度：
- 商业化变现
- 社交互动功能
- 技术架构优化
- 运营数据增长
- ...

**错误示范**：直接将"做了礼物动效"写入报告
**正确做法**：提炼为"商业化变现 - 礼物体系优化"，具体实现作为支撑细节

提供选项示例：
```
根据您提到的"直播间礼物动效"，这项工作可能属于：
1. 商业化变现 - 提升礼物转化率
2. 用户体验优化 - 增强互动反馈
3. 技术能力建设 - 动效渲染性能

请选择最符合本周工作重点的主题，或补充说明实际目标。
```

#### 3.4 生成报告内容

根据选定主题和用户提供的工作记录，生成四个章节内容：

**业务进展**：描述做成了什么，产生了什么影响
**风险与问题**：遇到了哪些阻碍或潜在风险
**解决方案**：如何应对这些问题
**下一步计划**：后续的行动方向

写作时注意：
- 使用业务语言而非技术细节堆砌
- 数据展示适度：如果用户提供了具体数字就使用，如果只是"大概"、"好像"，可以使用相对表述（如"显著提升"、"明显改善"）
- 控制篇幅：周报目标40-50行，每章节保持精简
- 风险问题点到为止：简要说明问题和影响即可，不需要过度展开"具体表现"、"影响范围"、"紧急程度"等细节
- 避免"完成了XX需求"这类流水账表达

#### 3.5 更新知识库

报告生成后，自动更新业务知识库：
- 将本次主题追加到该业务的历史主题列表
- 如果发现新的特性维度，更新核心特性列表

**重要**：使用追加模式写入，禁止覆盖已有内容。

#### 3.6 写入文件并标记元数据

在报告末尾添加元数据：
```markdown
---
_最后更新: YYYY-MM-DD HH:mm_
_迭代次数: 1_
```

周报生成完成！

## 迭代更新流程

适用于所有报告类型（周报/月报/年报）的增量更新。

1. 读取现有报告内容
2. 识别用户输入中的新增/变更事项
3. 判断变更类型：
   - **补充细节**：在对应章节追加内容
   - **修正信息**：替换或更新已有描述
   - **调整方向**：重新提炼主题（需用户确认）

4. 合并时保持原有业务逻辑连贯性，避免重复或冲突
5. 更新迭代标记（更新时间和迭代次数+1）

## 月报生成流程

月报是基于多个周报的跨周期总结。

### 步骤 1: 路径计算与节点判断

1. 使用脚本计算月报路径：
   ```bash
   bash scripts/calc-report-path.sh <date> monthly
   # 输出: ~/mico-work-summary/YYYY/MM/YYYY-MM.md
   ```

2. 检查是否已存在：
   - 若不存在 → 继续步骤2（新建月报）
   - 若已存在 → 跳转到[迭代更新流程](#迭代更新流程)

### 步骤 2: 扫描周报素材

使用脚本扫描本月所有周报：
```bash
bash scripts/scan-period-reports.sh <month_start> <month_end> ~/mico-work-summary
# 输出: 该月内所有周报文件路径列表
```

### 步骤 3: 请求用户补充月度视角

询问用户：
- 本月最重要的业务趋势是什么？
- 有哪些跨周的里程碑事件？
- 需要特别强调的成果或风险？

### 步骤 4: 生成月报内容

参考 `assets/monthly-template.md` 和周报素材，生成月报：

**关键原则**：
- **不要**重复罗列各周细节
- **要**提炼跨周期的模式和趋势
- **要**说明关键决策和转折点
- 长度约为单周报的2-3倍（非4倍）

遵循周报的[步骤3.2-3.6](#步骤-3-新建周报)（业务域处理、主题提炼、内容生成、知识库更新、写入文件）。

## 年报生成流程

年报需要同时生成两份报告。

### 步骤 1: 路径计算

使用脚本计算年报路径：
```bash
bash scripts/calc-report-path.sh <date> yearly
# 输出两个路径：
# ~/mico-work-summary/YYYY/YYYY-12-31-summary.md
# ~/mico-work-summary/YYYY/YYYY-12-31-self.md
```

### 步骤 2: 扫描全年报告素材

使用脚本扫描全年月报（如果有）或周报：
```bash
bash scripts/scan-period-reports.sh <year_start> <year_end> ~/mico-work-summary
```

### 步骤 3: 生成年度工作总结 (summary.md)

**定位**：面向协同方，展示"做成了什么"

1. 加载 `references/yearly-summary-guide.md` 了解写作要点：
   - 聚焦最重要的3-5项工作产出
   - 提供关键举措 + 关键结果
   - 包含具体业务数据
   - 明确项目角色、进度、结果
   - **不包含**敏感数据/关键业务信息

2. 使用 `assets/yearly-template.md` 作为结构骨架生成报告

### 步骤 4: 生成员工自评 (self.md)

**定位**：面向评审方，展示"做得怎么样"

1. 加载 `references/self-evaluation-guide.md` 了解自评结构

2. 使用 `assets/yearly-self-template.md` 作为结构骨架

3. 包含以下部分：

**第一部分：核心业绩与工作思考**
- 补充年度总结中不便公开的敏感数据
- 或展开全年工作的战略打法、关键举措、收获沉淀

**第二部分：个人复盘**（必填）
- 对比预期、未来发展、成功经验、根因分析

**第三部分：价值观**（可选）
- 基于正念/极端/简单/谦卑四个维度选择1-2个
- 结合具体行为案例撰写
- **详细参考**：`references/values-framework.md`（包含四大价值观详解、行为准则、践行场景示例、撰写指南）

**第四部分：管理自评**（仅 Leader，可选）
- 管好业务、带好团队、传好文化
- **详细参考**：`references/leadership-framework.md`（包含三大管理维度详解、评估标准、自评模板、丰富案例）

详细指导请查阅 `references/self-evaluation-guide.md`。

## 常见问题

**Q: 用户输入信息不足怎么办？**
A: 引导式提问，但避免连珠炮式发问。优先询问最关键的信息（业务目标、关键结果），次要细节可基于已有信息合理推断并让用户确认。如果用户只说"大概"、"好像"，不要强求精确数字。

**Q: 如何判断工作主题抽象层级？**
A: 参考历史主题记录和业务核心特性，保持一致的抽象层级。如果不确定，提供多个层级选项让用户选择。

**Q: 迭代更新时如何避免内容冲突？**
A: 先理解用户本次更新的意图（补充/修正/调整），再决定合并策略。如果发现矛盾，优先询问用户而非自行决断。

**Q: 跨周期汇总时如何控制长度？**
A: 月报基于周报提炼，不是简单拼接。关注跨周的趋势变化和里程碑事件，单周细节可以省略。年报同理。

**Q: 如何控制周报篇幅？**
A: 目标40-50行。业务进展10-15行，风险问题5-8行，解决方案5-8行，下一步计划5-8行。避免过度展开细节。

## 反模式警告

**流水账式汇报：平铺罗列任务清单**
- 问题：读者陷入细节，无法快速理解工作价值
- 做法：将具体任务归纳到业务主题下，说明"做成了什么"而非"做了什么"
- 示例：❌"本周完成了需求A、需求B、需求C" → ✅"本周聚焦商业化变现，通过优化礼物体系提升转化率"

**业务语言缺失：技术细节堆砌**
- 问题：业务读者难以理解技术术语，无法评估实际影响
- 做法：将技术动作翻译为业务结果，用数据说明改进效果
- 示例：❌"重构了UserService，优化了数据库查询，修复了3个bug" → ✅"解决了用户数据查询性能瓶颈，页面加载时间从3s降至0.5s"

**可信度损失：假大空表述**
- 问题：缺乏事实支撑，无法验证真实贡献
- 做法：明确角色定位（主导/参与/支持），提供量化结果
- 示例：❌"深度参与项目，全力推进业务发展" → ✅"主导XX功能设计与实现，上线后日活提升15%"

**数据安全风险：覆盖业务知识库**
- 问题：覆盖写入导致历史主题丢失，影响后续分析连贯性
- 做法：仅使用追加模式写入；如需修正，先读取全文再整体更新
